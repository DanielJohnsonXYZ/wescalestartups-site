## 1. THE GSC CONNECTOR FAULT IS THE SAME ONE RUN 19 FIXED, AND THE FIX IS NOW UNREACHABLE FROM HERE

`analytics_query` returned `Multiple google accounts found. Please specify an account boundary or remove unused accounts.` `accounts_manage list` shows four accounts:

```
google_1786027726098  daniel@wescalestartups.com   google
bing_1786030829503    Bing Account                 bing
legacy_google         Service Account (env)        google
legacy_bing           Bing API Key (env)           bing
```

That is precisely the state run 19 diagnosed and cleared: the extension's optional `user_config` fields are blank, the literal `${user_config...}` template string is passed through as an env var, and the server registers it as a credential source. **The remedy is `accounts_manage remove legacy_google` / `legacy_bing`, and this run's attempt to run it was denied by the permission classifier**, not by the connector. `analytics_query` exposes no `accountId` parameter, so there is no boundary to pass instead.

**Two things follow, and the second matters more than the first.**

1. **The recurrence is the finding, not the fault.** Run 19 removed these accounts on 2026-08-31. They are back on 2026-09-02, without Daniel reinstalling anything as far as the commit history shows. **`accounts_manage remove` therefore does not persist**, or the phantoms are re-registered at every server start from the still-blank config. Either way the playbook's instruction — "remove with `accounts_manage remove`; do not fill the fields in" — is a workaround that has to be repeated, not a fix. **Recorded as: this will recur, and a run that hits it has lost its GSC data for that run unless a human clears it.**
2. **A connector fault and a permission denial look identical from inside a run and are not the same thing.** Run 18's standing rule — *a connector reporting "unavailable" is a symptom, not a diagnosis* — was written about a server that would not start. This is a server that works, an operation that exists, and an authorisation layer that says no. **New rule: distinguish "the instrument is broken" from "this run is not allowed to use the instrument", and report the second to Daniel as an ask rather than logging it as an outage.**

**No `analytics_query` was ever issued without an explicit `siteUrl`** (the call that failed carried `sc-domain:wescalestartups.com`). The run-19 wrong-property trap was not tripped, because nothing returned at all.
