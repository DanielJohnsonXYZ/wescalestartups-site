# Addendum — the Search Console connector was never an auth problem

Daniel asked the bot to fix it rather than adding it to his own list. It is fixed, and the diagnosis that has been carried since run 17 was wrong.

## What was actually broken

`search-console-mcp` v2.1.2 (`local.mcpb.saurabh-sharma.search-console-mcp`) failed to start with:

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find package 'dotenv'
```

**The extension shipped without its `node_modules`.** No dependency tree, no lockfile, eleven unmet runtime dependencies. The server crashed on its first `import` every time Claude launched it, which the desktop app surfaces as "Server disconnected".

Fixed with `npm install --omit=dev --no-audit --no-fund` in the extension directory — 247 packages, 20 seconds. One benign warning: `protobufjs`'s postinstall script was blocked by npm's script policy; it is only reached through the GA4 path, which is not configured and is not part of this mandate.

## The run-17 diagnosis does not survive contact with the evidence

Run 17 recorded the connector as dead with `invalid_grant: Token has been expired or revoked`, concluded it needed Daniel to re-authorise, and put it at the top of "carry forward". Run 18's first report repeated it.

**Google auth was never broken.** After the install, with no credential change of any kind:

- Startup banner: `Search Console MCP running on stdio [ ✔ Google | ✘ GA4 | ✔ Bing ]`
- `sites_list` returns the full property list including **`sc-domain:wescalestartups.com`**, zero `invalid_grant` in the response
- `analytics_query` on 2026-08-02 → 2026-08-29, `dimensions: ["query"]`, returns real rows — `we scale` 4 clicks / 184 impressions / position 6.57, matching the Search Console UI figure this run pulled by hand

The likely sequence: run 17's `invalid_grant` came from a **different, older connector** exposing `gsc_*` tool names. This extension was installed at **21:38 on 2026-08-27**, about an hour after run 17 finished, and has never once started. So the auth failure was real, was fixed by Daniel installing the replacement, and the replacement then failed for an unrelated reason that looked identical from the outside — a dead connector.

**The transferable rule, and it is the same one run 16 and run 17 each learned separately: a connector reporting "unavailable" is a symptom, not a diagnosis. Run the server and read its stderr before writing down a cause.** Two runs carried "Daniel must re-authorise" as fact without once executing the binary. It took four commands.

## What this changes

- **`page,query` analysis is available again.** Every run since 17 has driven the Search Console UI by hand. Run 17 built two wrong diagnoses of `/gtm-strategy` partly because pulling its query set through the UI felt expensive; that excuse is gone.
- **Remove "re-authorise the GSC connector" from the blocked-on-Daniel list.** It was never the problem.
- **Daniel must restart Claude Desktop once** for the connector to be picked up; MCP servers are launched at session start, so it is not live in the session that fixed it.
- **This fix is fragile in the documented way.** Updating or reinstalling the extension will wipe `node_modules` and reproduce the failure exactly — the same trap already recorded for the Bing extension's vendored date patch. If the connector "disconnects" again, check for `node_modules` before checking anything else.

## Worth a look, not looked at

The server exposes `genai_query_insights`, `indexing_submit` and `indexing_status`. The playbook currently states "GSC MCP is read/inspect only — no request-indexing endpoint", which was true of the old connector and may not be true of this one. **Do not assume either way — call them and read what comes back.** Prohibition 18 still applies: do not spam indexing APIs or exhaust quotas.

## Addendum 2 — the connector is live, and it brought a new instrument

Daniel restarted the app. One further fault surfaced and was fixed, and the first `page,query` pull in four runs produced a number worth keeping.

### The second fault: two phantom accounts

The first live call returned `Multiple google accounts found. Please specify an account boundary`. `accounts_manage list` showed four accounts, and `diagnostics` explained why:

| Account | Status |
| --- | --- |
| `daniel@wescalestartups.com` (OAuth) | ok — 31 sites |
| `Bing Account` (OAuth) | ok — 39 sites |
| `Service Account (env)` | error — *key file no longer exists at `"/${user_config.google_application_credentials}"`* |
| `Bing API Key (env)` | error — `InvalidApiKey` |

**The two `legacy_*` accounts were built from unsubstituted template strings.** The extension's optional `user_config` fields were left blank, so the desktop app passed the literal `${user_config....}` text through as the environment variable and the server registered it as a credential source. Both removed with `accounts_manage remove`. `analytics_query` then returned rows matching the Search Console UI exactly (`we scale` 4 clicks / 184 impressions / position 6.57).

**If a fresh install ever re-creates them, remove them again rather than filling the fields in** — the working auth is browser OAuth, and the env path is a second, unnecessary credential route.
