## 1. RUN 4 VERDICT — the passage worked, ranked at position 1, and was worth nothing

Run 4 added a provider-answer passage and FAQs to `/services/90-day-growth-sprint`, targeting **provider intent** ("who runs / who offers / which agency provides"). Verdict due today. Judged on the provider-shaped query set on that page across three 28-day windows.

| Window | Provider-shaped impressions | Position range | **Clicks** |
| --- | --- | --- | --- |
| 7 Jun – 4 Jul (pre-run-4) | **51** | 1.0 – 5.5 | **0** |
| 5 Jul – 1 Aug | **41** | 1.0 – 9.0 | **0** |
| 2 – 29 Aug (post, 3+ weeks) | **2** | 7.0 | **0** |

The individual rows, August window, are the whole story — provider intent has all but vanished from the page:

- `our board set a 12-week deadline for a full brand refresh and site relaunch—who has a repeatable sprint process for high-growth saas?` — 2 @ 7.0

Against July, which had ten provider rows including `top providers of 90-day sprint marketing engagements for saas marketing teams?` @ **1.0**, `which saas marketing agencies provide the best 90-day sprint marketing engagement?` @ **1.0**, `who offers the best 90-day sprint marketing engagement in saas marketing?` @ **1.0**, and `get a quote for a 90 day growth sprint for my startup` 11 @ **4.0**.

**VERDICT: FAILED on the primary metric — zero clicks in three consecutive windows — and the failure mode is the finding.**

This is *not* the run-1 result. Run 1 failed at position 46 and taught that content is insufficient at position 45. Run 4 **succeeded at ranking**: it held **position 1.0** on half a dozen provider-selection prompts for two full windows. And it still produced zero clicks.

**The reason is that these are not human searches.** Every one of them is long, conversationally punctuated, ends in a question mark, carries 1–18 impressions, and sits at position 1.0. That is the AI-fanout / machine-issued signature this playbook already identifies elsewhere. `evaluate acme growth studio on 90-day sprint marketing engagements` is not a buyer; it is a machine comparing vendors, and one of them is a placeholder name.

**Two conclusions, marked by confidence:**

- **VERIFIED: winning position 1 on provider-fanout queries produces no clicks.** Three windows, 94 provider impressions, zero clicks, positions 1.0–9.0. There is no click to be had at any rank on this query class.
- **INFERRED: the provider pool is not a pool WSS lost — it evaporated.** Positions stayed at 1.0 right up until the queries stopped appearing. That is Google changing its fanout behaviour, not the page losing ground. n is small; do not over-read.

**What this changes.** The playbook's best rule — *this site ranks for questions, not keywords* — needs one qualification added, not a reversal: **it matters whether a human asked the question.** Machine-issued provider fanout ranks easily and pays nothing. Human question-shaped demand (`should a series a startup hire a fractional cmo…`, 40 impressions @ 7.65) is a different and still-untested animal. Run 5's verdict on 2026-09-08 is the first honest test of the human half.

**Do not re-optimise this page for provider intent.** Do not read the disappearance as a regression. And critically: **do not confuse this with run 15's verdict on 2026-09-17**, which is about the *informational* queries on the same URL — and which moved hard in the opposite direction.

## 3. FIFTH FALSE FACT IN THE PLAYBOOK — and this one had been acted on for eight runs

The playbook said, as a standing instruction:

> `/facts/*` carry `lastUpdated` — keep fresh monthly.

**They did not carry it.** Neither `/facts/we-scale-startups` nor `/facts/daniel-johnson` passed `lastUpdated` to `BaseLayout`, so no freshness band rendered on either page and no `dateModified` reached their JSON-LD. The instruction had been sitting in the file as a maintenance task that was structurally impossible to perform, and no run in eight noticed, because every run read the claim instead of the page.

Same shape as the other four: a half-truth never re-checked against the primary source. **The wrong line is deleted, not annotated.**

**The fix is better than the claim was.** Rather than passing `siteConfig.lastUpdated` — which is hand-maintained and currently reads **"6 August 2026"**, i.e. would have published a stale date on the one page where freshness matters most — the page now derives its label from the **generated** `staticPathLastModified` map. The visible date and the sitemap `lastmod` are now the same generated value and cannot drift apart. Nothing to remember monthly.

`/facts/daniel-johnson` still has no freshness signal. Left alone deliberately: one substantive change per run, and it is a separate page with no evidence pressure on it. Queued as backlog 14.

## 4. THE INSTRUMENT TRAP THAT ALMOST WROTE A FALSE VERDICT

The first GSC pull this run — dispatched to a subagent with the property named in the prompt but not enforced as a parameter — came back with:

> "Run 4 verdict: no data exists. The page has zero impressions in all three windows, and it is not in Google's index at all. URL Inspection: coverageState **'URL is unknown to Google'**. The entire property contains only six pages, all on `www.` with WordPress-style paths."

Every sentence of that is a faithful report of a **different property**. The account holds 31 sites, including a stale `https://www.wescalestartups.com/` URL-prefix property left over from the pre-May-2026 WordPress site. **`analytics_query` does not error when `siteUrl` is omitted — it silently answers about whichever property it picks.**

Had this run trusted it, run 4's verdict would have been "the page was never indexed", the playbook would have gained a sixth false fact, and the next run would have opened by trying to fix a crawl problem that does not exist.

**The tell was in the data, not the tool:** WordPress paths (`/seo-services/`, `/portfolio/equoo/`) on a site rebuilt in Astro four months ago. Re-pulled with `siteUrl` passed explicitly and the real window returned 6,552 impressions across 95 pages.

**New standing rule, and it generalises past this connector: pass the property on every call, and sanity-check the returned URLs against the site you think you are measuring before reading a single number.** Recorded in the playbook's connector notes.
