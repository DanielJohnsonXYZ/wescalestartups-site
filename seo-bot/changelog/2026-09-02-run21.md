# ADDENDUM — same day, attended, after Daniel unblocked the instruments

Daniel read the report and responded within the hour. **Everything above about the blackout was resolved in four tool calls, and one of my diagnoses in §1 was wrong.**

## A. CORRECTION — Bing was never a separate fault. Delete the InvalidApiKey line.

§1 and the table at the top of this log record two faults: phantom accounts killing GSC, and Bing returning `InvalidApiKey`. **That is one fault, not two.** Removing `legacy_bing` fixed Bing in the same stroke as `legacy_google` fixed GSC — `sites_list` and a live `analytics_query` against `https://www.wescalestartups.com/` both returned full data immediately afterwards, with no key change and no re-authorisation.

The blocked account list in §1 is right about the mechanism and wrong about the count. **One cause, four symptoms.** Recorded here rather than edited above, because the wrong inference is the thing worth keeping visible: I had a working explanation for GSC, saw a second connector fail, and wrote it up as a second problem instead of the same one. **The tell was available and I did not use it — `accounts_manage list` shows the Bing phantom sitting right next to the Google one, in the output I had already pulled.**

## B. ROOT CAUSE — the phantoms are recreated at every server start, and the playbook's fix was the cause

Read `dist/common/auth/config.js` in the extension. It rebuilds the account list from environment variables on **every** launch:

- `legacy_google` if `GOOGLE_APPLICATION_CREDENTIALS` is set, or `GOOGLE_CLIENT_EMAIL` + `GOOGLE_PRIVATE_KEY`
- `legacy_bing` if `BING_API_KEY` is set
- both guarded by `if (!config.accounts[id])`

**So `accounts_manage remove` deletes from the saved config and the next launch re-derives it.** That is the whole recurrence: run 19 cleared them on 2026-08-31, the app restarted, they came back by 2026-09-02. It is not a mystery and it is not a new bug each time.

The variables are set because the extension declares them and the **blank optional fields are passed through as the literal string `${user_config.…}`, which is non-empty and therefore truthy.** So the playbook's standing instruction — *"Remove with `accounts_manage remove`; do not fill the fields in"* — **names the cause as the cure.** Blank is what creates them.

The clean fix means reinstalling the extension without those optional fields, or editing its manifest. **I was blocked from reading the manifest** (the search matched credential-shaped names) and did not route around it. **The practical fix agreed with Daniel is to let the bot heal itself**: `mcp__search-console-mcp__accounts_manage` added to the permission allow-list, so a future run clears the phantoms in one call instead of losing its Google and Bing data for the day.

## C. THE BROWSER WAS NEVER BROKEN — and this is the structural finding of run 21

Chrome connected on the first call of the attended session. **The scheduled run was refused because it was unattended, not because anything was wrong.** §2's framing — "both browsers were denied" — is factually right and diagnostically misleading: it belongs in a different category from the connector fault.

**New standing distinction, now in the playbook: an instrument can be broken, or this run can be forbidden from using it. They present identically and they need opposite responses** — the first is a bug to diagnose, the second is a permission to request, and no amount of diagnosis will fix it.

**Consequence, and it is the one that changes how this bot is scheduled:** an unattended run cannot use a browser at all. That permanently removes the AI panel (the only prompt-level instrument) and the GSC Generative AI report (UI-only) from every scheduled run. Run 21 shipped without either.

It also fixes the cadence problem run 20 raised: three runs a week against a Search Console window that advances every two to three days.

**One correction to §5 of this log while I am here:** the "stops when the app closes or this computer sleeps" warning is not what broke run 21. Run 21 fired on time at 07:18, as did four other scheduled tasks that morning. Sleep was never implicated. **Do not fix a problem the evidence does not show.**

## H. CONNECTOR DEFECT — `analytics_query` returns the WRONG PROPERTY on `page` and `query` dimensions EVEN WITH `siteUrl` SUPPLIED

With `siteUrl: "sc-domain:wescalestartups.com"` passed explicitly on every call:

- `dimensions: ["date"]` → **CORRECT property.** Verified by cross-reference, not by trust: 25 Aug 215 impr / 4 clicks · 26 Aug 651 / 4 · 27 Aug 529 / 1 · 28 Aug 163 / 0 · 29 Aug 180 / 1 are **identical to the figures run 20 logged** for the right property.

**So the dimension determines which property answers, and `siteUrl` does not override it.** Whether this predates today's removal of the phantom `legacy_*` accounts is **unknown and untested** — do not assume the removal caused it.
